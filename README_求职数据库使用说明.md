# 求职投递追踪数据库 — 使用说明

版本：2026-09-24（第二版：新增模式分析、更正 applications 渠道字段）

## 这是什么

`job_search_tracker.db` 是一个 SQLite 数据库，把之前已经核实过的 Gmail 求职数据固化下来。以后有新的分析需求，先查这个库，不用重新翻一遍 Gmail。

数据库里有5张表：

1. **monthly_stats**：2025年3月到2026年9月，每月投递量（JobStreet / LinkedIn / 直投）和当月收到的结果（拒信 / 过期 / 查看待定），19行，已逐个数字和原始看板核对过。
2. **rejection_sample**：拒信原因抽样核查，2025年3月到2026年8月，每月约5封带反馈详情的 JobStreet 拒信逐封读过。合计75封打开、70封有反馈、65封（93%）标注工作权限不匹配，5个例外记录了公司名和实际理由。
3. **companies**：9家研究核实过的公司（5个例外 + 4家获得面试邀约的公司），规模判断依据是弱证据，不是工商注册雇员数。
4. **applications**：2026年9月前后在跟进的36份投递。渠道字段只保留有明确证据的（JobStreet编号、LinkedIn编号、写明邮件或猎头），其余22份为 unknown，依据写在 channel_evidence 列。
5. **meta**：数据核实日期、更正记录和数据质量警示，共8条。

## 模式分析结论（analysis.py 可重跑）

**发现1：拒信数量由 JobStreet 投递量决定，比例稳定在约58%。** 每月拒信数和当月 JobStreet 投递数的相关系数是0.95，回归截距约为0，斜率0.577。换成上个月的投递量，相关系数掉到0.48，说明拒信大多在投递当月就到。投递量40份以上的11个月里，拒信比例平均57.5%。

**发现2：硕士毕业没有改变拒信比例。** 毕业前拒信/JobStreet投递为56.3%，毕业后为58.2%。雇主查看率从14.6%升到17.7%，但 z=1.74，没有达到统计显著。

**发现3：拒信原因的抽样结果和发现1、2吻合。** 70封有反馈的拒信里65封标注工作权限不匹配。拒信里列出的项目（工作权限、期望月薪、相关岗位年资、资历类型、SQL 经验年资）看起来就是 JobStreet 投递流程里雇主设置的筛选问题。这是根据字段内容做的判断，没有从 JobStreet 官方文档核实，下次投递时留意"回答雇主问题"那一步就能自己确认。如果成立，拒信是由筛选问题的答案自动触发的，所以才会跟投递量同步、不受学历变化影响。

**对5个例外的解释：** 它们更可能是雇主没把工作权限设为筛选条件，跟公司规模关系不大（Sanmina-SCI 是大型跨国公司，也在例外里）。5个例外里有2个（都在2026年）写了期望月薪不匹配，样本太小，只能算一个待验证的线索。

**无法从现有数据得出的结论：** 公司规模或行业和拒信理由的关系（例外只有5个，另外65封没记录公司名，没有对照组）；面试来源的规律（邮件里只有4次面试记录，大部分面试是电话/WhatsApp 约的）。

## 数据质量警示

- **过期数 > JobStreet 投递数。** 累计过期通知964条，累计 JobStreet 投递912份；2025年5月时已经是41条对28份。所以"964个帖子过期"不能全部理解为"我投的岗位没有回音"：要么包含收藏但没投的岗位，要么 JobStreet 投递数有漏计，需要在邮件层面核实。之前的看板和给父母的 PDF 用的是同一个964。
- **applications 表的渠道已更正。** 第一版里有部分渠道是构建时推断的，这一版已改为没有证据就填 unknown。

## 以后怎么用

1. 打开数据库：用 Python 的 sqlite3 库，或安装 sqlite3 命令行后运行 `sqlite3 job_search_tracker.db`。
2. `query_examples.sql` 有7条常用查询，`analysis.py` 可以重跑上面的模式分析。
3. 有新需求先查数据库，缺数据再查 Gmail，只查 meta 表里核实日期之后的新邮件。
4. 追加数据直接用 INSERT/UPDATE。`build_db.py` 会先删旧库再重建，只在需要从头重建时用，而且要和 `schema.sql` 放在同一目录。

## 文件清单
