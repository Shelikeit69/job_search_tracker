# 求职投递追踪数据库 — 使用说明

## 这是什么

`job_search_tracker.db` 是一个 SQLite 数据库，把之前已经核实过的 Gmail 求职数据固化下来。以后再有新的分析需求（比如"某个月份对比""哪个渠道效率高""拒信原因有没有规律"），先查这个库，而不是重新让 Claude 翻一遍 Gmail 全部邮件。

数据库里有5张表：

1. **monthly_stats** — 2025年3月到2026年9月，每月的投递量（按JobStreet/LinkedIn/直投拆分）和收到的结果（拒信/过期/查看待定）。来自"投递全记录"看板，19行，已逐个数字和原始HTML核对过，没有录入错误。
2. **rejection_sample** — 拒信原因抽样核查记录，2025年3月到2026年8月，18个月，每月抽样约5封带反馈详情的JobStreet拒信逐封读正文核实的结果。合计75封打开、70封有反馈、65封（93%）标注工作权限不匹配，5个例外单独记录了公司名和实际拒信理由。
3. **companies** — 只收录已经核实研究过的9家公司（5个例外案例 + 4家已获得面试邀约的公司），包含行业、规模判断和判断依据。规模判断都是"查不到中文品牌/公开资料"这类弱证据，不是工商注册的精确雇员数，用的时候要知道这一点。
4. **applications** — 当前在跟进的36份投递（2026年9月前后），来自你Obsidian/memory里的追踪记录，包含公司、职位、行业、渠道、状态。
5. **meta** — 记录每张表的数据核实到哪一天，增量更新时先看这张表。

## 关于"有没有可辨识的模式"这个问题的结论

**5个例外案例（拒信里完全没提工作权限的）里，4个是新加坡本地中小型私营公司，1个是大型跨国公司（Sanmina-SCI）。行业上没有聚集——贸易、金融服务、会计审计、电子制造各不相同。**

老实说这个"4:1"的规模倾向不能算一个站得住脚的规律，样本只有5个，任何一个都可能是巧合，Sanmina-SCI这个大公司的存在本身就打破了"只有小公司才不提"的假设。真正能验证这个问题的做法是把另外65封"确实提了工作权限"的拒信也一一记下公司名和规模，跟这5个做对照——这个我没有做，因为这需要重新逐封打开另外65封邮件核实公司身份，工作量不小，如果你想让我做可以另开一轮。

## 以后怎么用（给之后的 Claude 会话看）

1. 打开数据库：`sqlite3 job_search_tracker.db`，或者用 Python `sqlite3` 库连接。
2. `query_examples.sql` 里有7条常用查询，直接抄着改。
3. 新的分析需求，先跑数据库查询，缺什么数据再决定要不要查 Gmail——而且只查 `meta` 表里 `as_of` 日期之后的新邮件，不要重新扫描全部历史。
4. 如果要往库里加新数据（比如追加一个月的月度统计，或者补充某家公司的行业信息），直接用 `sqlite3` 的 `INSERT` 或 `UPDATE`，不需要重新跑 `build_db.py`（那个脚本会先删掉旧库重建，只在数据库损坏需要从头重建时才用）。
5. `build_db.py` 保留作为"数据来源记录"，每一行数据后面都注明了来自看板的哪个表格/哪个数组，方便以后核对。
